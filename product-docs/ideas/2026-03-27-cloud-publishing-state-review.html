Cloud Publishing Review

Cloud Publishing and Reconciliation for Editable Scripture

A review artifact for moving from clarified product intent into pseudocode and beads. Framed as cloud publishing and reconciliation, not generic remote sync.

Scope
Web + Tauri One shared domain design, with platform-specific transport underneath.
Primary User Story
Publish Local editable project to cloud-linked project to repeated save-and-publish.
North Star
Transparency No silent USFM merges, no hidden local edit loss, no raw Git UI.
Conflict Basis
Latest Left / Right Reconciliation UX is based on current in-memory work versus remote latest state.
1. North Star

This feature extends Dovetail’s existing local-first save and history model. It does not replace it. The product is a scripture-focused cloud publishing layer with explicit review at sync boundaries, especially for USFM. Local save remains authoritative. Remote publication and remote intake are secondary operations with bounded failure states.

Hard Rules
  • Editable scripture projects only in v1.
  • One tracked branch only; no branch-management UI.
  • App-created remotes use master; cloned repos track remote default branch.
  • Export/share strips .git and Dovetail link metadata.
  • Session is app-global; token and mutable sync state stay app-local.
UX Commitments
  • No silent USFM merges; even separate-book or separate-chapter changes are surfaced.
  • No local edit loss; resolved state becomes unsaved working state until explicit save.
  • No raw Git terminology in normal UI.
  • Web cannot feel visibly worse than Tauri.
  • One-button bias for non-technical users, with explicit sync still available.

3. Session Machine

The session machine is app-global. It owns the current logged-in account and bearer token, plus bounded retry state for logout token deletion. It does not own project linkage or project cloud status.

  • Retry is bounded, not endless

  • No multiple active sessions
  • No portable session state

5. Networking Policy Machine

The cloud feature is not just project state. It is also governed by user policy. In the current codebase, settings already form a cross-platform seam through the shared settings manager. Auto-sync and auto-push should be modeled as explicit guards, not hidden conditionals scattered across save and open codepaths.

  AutoSyncOnOpen --> AutoBoth : EnablePushOnSave
  AutoPushOnSave --> AutoBoth : EnableOpenSync

  AutoSyncOnOpen --> ManualOnly : DisableOpenSync
  AutoPushOnSave --> ManualOnly : DisablePushOnSave
Guarded Open Event
  • OpenProject may trigger cloud check only in AutoSyncOnOpen or AutoBoth.
  • Even when enabled, open should not block the editor shell.
Guarded Save Event
  • Review & Save always performs local save and local commit first.
  • Cloud publish is entered automatically only in AutoPushOnSave or AutoBoth.
Explicit Escape Hatch
  • Sync remains available even in ManualOnly.
  • Settings act as default guards, not capability removal.

USFM Rule
  • Always explicit review when remote latest differs.
  • Separate-book and separate-chapter changes still surface; no silent merge.

  • User-edited content in v1 is USFM only.

  • Derived metadata is regenerated before save/publish.
7. State Ownership

This split is the most important architecture correction from the stale plan. It keeps linkage durable without polluting commit history with ephemeral app observations.

State / Fact Owner Why Review Outcome
hostBaseUrl, repo owner/name/id/url, tracked branch Project Local Durable linkage fact; enough for Dovetail to repair Git internals and know what the project belongs to. Keep in a small Dovetail-owned file inside the project.
Current account, bearer token, token deletion retry data App Local Session is install-specific and should never travel with a project. Store in app settings storage.
offline, pendingPublish, needsReview, lastChecked Per-Project App Local These belong to the project conceptually, but they are still machine-local observations about this install’s cloud relationship. Persist keyed by project, but do not track in Git or travel in exports.
Manifest checksums and similar scripture-derived metadata Derived Should be recomputed from accepted scripture state, not treated as primary user-edited content. Regenerate before save/publish.
Manual copied .git without Dovetail link file Ignore By Default Automatic adoption would violate explicitness and create ambiguous cloud linkage. Require explicit reconnect.
Export/share zip output Sanitized Recipients should not inherit private linkage they cannot actually use. Strip .git and link file.

9. Open Risks

These are the design risks that should shape pseudocode and beads next. They are not blockers to planning, but they are the places where correctness and product trust are easiest to lose.

Review Plumbing
  • Combined save-and-sync review must not duplicate or fight the existing unsaved diff modal.
  • Remote latest should slot into compare-source loading without introducing a second review stack.
  • Resolved state must land in working memory cleanly, then behave like ordinary unsaved edits.
Metadata Rewrite Rules
  • Derived manifest and checksum updates need an explicit regenerate-before-save step.
  • Non-derived metadata changes need a documented last-wins or preserve-remote rule.
  • The app must avoid creating noisy conflicts over files the user never edits directly.
Cross-Platform Truth
  • Web and Tauri need the same visible states and recovery behaviors.
  • Background open-time sync cannot feel blocking or surprising on Web.
  • Auth and remote Git assumptions need to hold equally for both platforms.
Product Trust
  • Users need plain-language statuses: connected, syncing, offline, changes not yet published, remote updates available, needs review.
  • One-button defaults are fine only if the machine states remain inspectable.
  • Explicitness matters more than cleverness for scripture content.

This artifact is meant to be the handoff surface into pseudocode and bead decomposition: the state ownership split is now pinned down, the major machines are named, and the extension points in the current repo are identified without pretending the old plan still matches reality.

Scripture Editor — how the whole thing fits together

~429 TS/TSX files · ~78k LOC · offline-first · Lexical + USFM + local git + cloud sync

This is a WYSIWYG scripture (Bible-translation) editor that runs both in the browser (OPFS + isomorphic-git + WASM) and as a Tauri desktop app (native fs + Rust git + WASM). It is offline-first: every project is a real git repo on the device, edits live in memory as a single source of truth, and the cloud is an optional remote you publish to and reconcile with. The hard parts — and the reason the codebase is large — are the three first-class lifecycles between disk and cloud: Load → Active edits → Save → (Publish), each with explicit command boundaries rather than scattered side effects.

React 19 + TanStack Router/Query Lexical (rich text) Effect (streams · pipelines) usfm-onion (Rust/WASM) isomorphic-git / native git
How to read this The TOC follows the data: from the layering down to the one live store, then outward through the editor, the mutation seam every active edit funnels through, and the three lifecycles (save, recovery, cloud). 00

Orientation — the mental model

Five ideas explain almost everything. Hold these and the rest of the map is detail.

A One live truth

WorkingFilesStore holds the canonical in-memory state of every open book/chapter. The editor, actions, save, sync — all read and write here. Nothing else is authoritative.

B Commits, not setters

You don't mutate the store in place. You commit(patch, meta). Every commit publishes a typed CommitEvent on two channels: React (render) and Effect (derived pipelines).

C Lifecycles are commands

Load, Save, and Cloud reconciliation are named, ordered, gate-owned command boundaries (runSavePipeline, runIncomingReconciliation) — not fan-out effects.

D One mutation seam

Every active edit (format, lint-fix, match) goes through withWorkingFilesDraft: draft → compute → validate → commit → invalidate. It makes lost-updates and stale writes structurally impossible.

E Pure core, adapter edges

src/core is platform-agnostic domain (USFM, git models). src/web / src/tauri implement the interfaces. src/app orchestrates. Core never imports app.

Why it's big

USFM is a gnarly markup format, the editor supports three lossless representations and three editing modes, and "saved ≠ versioned ≠ published" each needs its own honest state. The size is the lifecycles, not the widgets.

02

Boot sequence

Each platform main.tsx assembles its concrete adapters, then hands them as interfaces to one shared <App />. The marker catalog is initialized before first render so the editor's taxonomy is always available.

  1. Platform main (src/web/main.tsx · src/tauri/main.tsx) creates the settings manager, applies color scheme, resolves StorageRoots + FileSystem.
  2. Assemble adapters: git provider, usfm-onion service, auth session provider, Gitea remote provider, importer, opener (+ updater on tauri).
  3. Initialize the marker catalog — initializeUsfmMarkerCatalog(await usfmOnionService.getMarkerCatalog()). This populates the module-level registry that markerTaxonomy and validity checks read on the render path.
  4. Mount providers (src/app/entrypoint.tsx): i18n → QueryClient → theme → notifications → updater banner → RouterProvider, with all services bundled into router context.
  5. Reconcile the project index (projectsService.reconcileIndex()) so the Dexie/IndexedDB catalog matches disk before any route loader runs, then render the matched route.
03

The kernel — WorkspaceContext

The main editor route ($project.index.tsx) mounts one provider that composes every workspace concern and forks the Effect pipelines. It is honestly a kernel — but not everything must live inside it; it's the wiring point, and most logic lives in the modules it composes.

What it owns / composes

  • Stores: workingFilesStore, interactionGate, recoveredConflictTracker, lint/save-status/layout-tick/search-highlight stores, baseline + dirty-buffer stores.
  • Composed hooks: useWorkspaceState, useActions, useSave, useLint, useCustomHistory, useSearch, useReferenceItem, useRemoteSync.
  • Forked pipelines: lint, save-status, overlay-tick, dirty-buffer, recovered-conflict subscriber, structure-maintenance (via useForkedPipeline).
  • The editor handoff: mainEditorDeferred (an Effect Deferred) the bridge plugin resolves once Lexical mounts.

Why a kernel is fine here

The workspace genuinely is the unit of composition: every concern needs the same nouns (the store, the gate, the project). Centralizing the wiring keeps the seams visible.

The discipline: the kernel forks pipelines and passes stores, but the behavior lives in the pipeline modules and domain services. When a concern grows, it moves to its own module and the kernel keeps a one-liner — see useForkedPipeline collapsing six fork/interrupt effects into one call.

04

One live truth — WorkingFilesStore & the commit model

The store holds one array of ScriptureBookState. Writers call commit(patch, meta); the store applies a structural-sharing patch and fans the resulting CommitEvent out on two decoupled channels.

The dual-channel fan-out: synchronous React, async Effect.

Loading…

Patch kinds how the write is shaped

  • bulk — replace the whole files array (project-scope: import, version revert, seam commits).
  • chapter — update one chapter's lexical state; recompute dirty by token equality (the editor bridge's normal path).
  • metadata — flip a chapter's dirty flag only (save marks clean).
  • selectionOnly — signal-only; state unchanged (cursor moves, published as metadataOnly).

CommitMeta why subscribers can filter

Every commit is stamped with: kind (userEdit · programmaticFix · import · undo · redo · load · structuralFixup · metadataOnly …), scope ({bookCode,chapter} or {project:true}), dirtyTextContent (did visible text change?), and a monotonic generation.

Pipelines filter on this so not every commit triggers every pipeline — e.g. lint ignores metadataOnly/load/undo; structure-maintenance only reacts to userEdit with dirtyTextContent (so it never feeds its own loop).

Structural sharing draftWithChapters(refs) returns a shallow clone where only the named chapters (and their parent books) get fresh object identities; everything else aliases the live state. That preserves React.memo stability and is the exact boundary the lost-update validator checks (object identity, not text). src/app/state/WorkingFilesStore.ts

Effect pipelines — derived state, reactively

Each pipeline subscribes to workingFilesStore.changes (an Effect Stream fed by an unbounded PubSub), filters by commit meta, applies its own backpressure, and writes a derived store. They're forked once per workspace and interrupted on unmount via useForkedPipeline.

sousPipeline Content commits by sousScopeFor (book grain) Content analysis (scripture-sous-chef) → findingsStore sous slice + segment-map sidecar folded scope + debounce 200ms
dirtyBufferPipeline Content commits (excludes load / selectionOnly) Write/clear per-book USFM crash backup groupByKey per book · debounce 500ms · staleness ceiling 10s · retry w/ backoff

editorSyncPipeline Programmatic commits (incoming sync / fixes) touching the open chapter Push store changes back into the live editor None (immediate)

The editor — Lexical + USFM

A custom Lexical document where USFM semantics live on the nodes. The same content round-trips losslessly between three representations and renders in three editing modes.

CUSTOM NODES

Node Extends Role
USFMParagraphNode ElementNode Paragraph-class container (\p, \q1, \s1…); carries id/marker/sid metadata via NodeState so structure survives editing.
USFMTextNode TextNode The leaf for every visible token — text runs, marker openers/closers, verse numbers. Carries tokenType/marker/sid/attributes.
USFMNumberedMarkerNode USFMTextNode Structured chapter/verse markers (\c, \v). Token emission derives from node shape (openBytes / number text / closeBytes) — no hidden editable marker bytes; the number is the only editable content.
USFMNestedEditorNode DecoratorNode Footnotes / cross-refs (\f, \x) as a nested Lexical editor rendered inline — atomic to the outer doc, fully editable inside.

BookFrontmatterFormNode DecoratorNode Form-mode card for chapter 0 (book metadata) — frontmatter fields, not verses.

KEY PLUGINS

The only path from editor → store. On each update it classifies the commit kind (userEdit / undo / structuralFixup / programmaticFix), skips programmatic round-trips, and calls workingFilesStore.commit. Selection-only updates publish as metadataOnly.

FindingsOverlayPlugin

Renders findings from both producers: token-anchored (lint) highlights resolve to their token element, or a badge when off-screen; content-anchored (sous) findings resolve (sid, UTF-16 span) to DOM rects via the vref segment map. Suppressed for form-shape findings (form has its own affordance).

ContextMenuPlugin

Right-click / Cmd-K → the action palette, positioned at the cursor, carrying the current EditorContext.

VerseMarkerSuggestPlugin

Detects a leading number that should be a \v and offers an inline "promote to verse" affordance.

USFMPlugin

Composition root — wires input/view listeners and mounts the sub-plugins.

Listeners

manageUsfmMarkers + maintainMetadata keep derived metadata in sync on input (sids, inPara, structural-empty), tagged so the bridge marks them structuralFixup. The old full-document repair sweep is gone — structured nodes make the corruptible states unrepresentable.

THE THREE-REPRESENTATION BRIDGE

The token stream is the lossless pivot — modes are just different Lexical shapes over the same tokens.

Loading…

regular shape: regular

WYSIWYG: USFMParagraphNode containers; chapter/verse markers are structured USFMNumberedMarkerNodes (shape-derived bytes, editable number); char markers hidden; notes as inline badges. (view is the read-only twin.)

usfm / plain shape: flat

One paragraph wrapping the flat token stream. usfm shows marker markup; plain is pure text.

form shape: form

Card-based structured editor: each paragraph block is a FormBlockNode card; chapter 0 is a frontmatter form.

Marker taxonomy (single source) Form-mode block categories (heading / poetry / list / paragraph) and the section test now derive from the usfm-onion catalog's paragraphCategory (v0.0.5+) via markerTaxonomy.ts — not hand-maintained sets. Only two small local maps remain, both labeled: the app's rule grouping (\b/\pb) and a handful of legacy markers the catalog doesn't enumerate. Regular-mode node shape likewise derives from catalog payload / closingBehavior (v0.0.7+), never marker-name lists.
08

The mutation seam — withWorkingFilesDraft

Every active mutation (format, prettify, match-formatting, lint-fix) and every incoming-sync write goes through one validated boundary. It makes the lost-update and stale-write hazards structurally impossible, and guarantees no UI side effect fires for a write that didn't land.

draft → compute (async ok) → re-validate → gate-check → commit → invalidate.

Loading…
Contract mutate may only touch the scratch and compute a value — no UI/lint/editor side effects (the commit isn't validated yet). All side effects move to invalidate, which runs only after a validated commit. On abort, neither invalidate nor any caller effect runs. The same validated primitives back the incoming-sync path (applyIncomingToStore / runIncomingMutation) so there is one lost-update contract in the codebase.

Two commit scopes

chapters (default) — overlay only the affected chapters onto the latest read; a concurrent edit to other chapters survives. workspace — the mutator rebuilt whole chapters arrays (e.g. rebuildParsedFileFromUsfm), so validate by array identity then commit the scratch wholesale.

Why identity, not text

The store gives a touched chapter a new object on any commit. Comparing identity catches a text edit and a save-rebase that changed sourceTokens/dirty but not the visible text — both must abort. selectionOnly commits don't replace chapters, so cursor moves don't false-abort.

09

Save lifecycle — runSavePipeline

Save is a UI-free, ordered command. It gates the workspace, freezes a snapshot, writes bytes, then advances the version checkpoint and (optionally) publishes — reporting substates the hook turns into toasts.

Phases run in order; each phase has an honest failure mode.

Loading…

SaveResult UI-free outcome

  • saved — { persistedBookCodes, checkpoint, publish }
  • partial — some books persisted, then a write threw
  • failed — pre-write failure, nothing on disk
  • blocked — { reason } (gate closed / conflicts unreviewed)

The pipeline imports no notification API; useSaveAndRevert renders the success toast + checkpoint/publish warnings from this result.

The honest baseline rebase

After bytes land, in-memory chapters still read dirty. The pipeline advances each persisted book's baseline to the captured tokens (frozen up front, not live currentTokens) so a keystroke mid-save isn't silently swallowed, then re-derives dirty. Books that failed to persist keep their dirty state.

Line endings preserved Each chapter remembers its disk line ending (eol); the serializer (tokensToUsfm(tokens, eol)) re-applies it, so a CRLF file round-trips without a whole-file phantom diff. The editor model is LF-internal.
Cross-cutting decision "Saved to disk" ≠ "versioned" ≠ "published." A checkpoint or publish failure is a warning, not a save failure — the bytes are safe on disk and the books are marked clean regardless.
10

Crash recovery & the interaction gate

Two orthogonal safety surfaces keep edits honest across crashes and concurrent operations.

Coarse — the gate

WorkspaceInteractionGate blocks all mutation while saving or while a restore decision is recovery-decision-pending. Every mutation entry point calls requireGateOpen; buttons render disabled. It's the deeper net the seam re-checks at its synchronous commit boundary.

Fine — recovered conflicts

The dirtyBufferPipeline continuously writes per-book USFM backups while dirty. At reopen the recovery loader classifies each backup: baseline matches disk → safe auto-restore; baseline moved → a recovered conflict tracked in RecoveredConflictTracker, which forces saves through review and blocks incoming sync until resolved.

Leave work in the dirty buffer Recovery deliberately restores work into the live editor for the user to review as diffs — it does not auto-commit. The reviewer flicks through dirty files, not through micro-commits.

Cloud sync — the remote lifecycle

The cloud is optional. A project may be linked to a Gitea remote; its durable GitRemoteProjectStatus.kind is the state machine the UI reads. Sync is a pure policy decision followed by publish or reconcile.

Six durable status kinds. Edges are the events that move between them.

Loading…

Relationship → status

The pure classifier classifyGitRemoteRelationship({localHead, remoteHead, mergeBase}) yields one of untracked · upToDate · aheadOnly · behindOnly · diverged, which gitRemoteLifecycle maps to status: upToDate→connected, behindOnly→remoteUpdatesAvailable, diverged→needsReview, aheadOnly/untracked→pendingPublish.

decideRemoteSyncAction

Before any IO, a pure policy: pendingPublish → publish (always); gated or unresolved-conflicts → refresh-only{reason}; remoteUpdatesAvailable/needsReview with auto-accept → auto-accept-incoming{suppressReviewModal}; else refresh-only.

INCOMING RECONCILIATION

How a freshly-pulled remote-latest gets adopted — or held for review.

Loading…
Invariant — never accept while review remains runIncomingReconciliation returns one outcome; the hook applies it once. A pure finalizeOutcome drops the behind-only fast-forward whenever any review diff remains, keeping remoteSync attached so the next save adopts remote latest. You cannot mark the remote accepted while the user still has diffs to review.
Publish coordinator — one publish, two doors publishWithCurrentSession is the only push. publishLinkedProjectAfterSave (save pipeline) honors the autoPushOnSave setting; publishLinkedProjectNow (explicit sync) ignores it. Both translate the push outcome (published · offline · remoteAdvanced · authFailed) into the durable status.
12

Compare & diff

A semantic diff engine (in usfm-onion) compares the workspace against a source — remote latest, another project, a zip/dir, or an older version — and produces per-chapter diff blocks the DiffModal renders for review and selective accept/revert.

compareService

buildCompareResultAsync diffs current files vs source files in chunks (yielding to the main thread), producing diffsByChapter + warnings + metadata.

Semantic vs cosmetic

Each diff block carries a semanticSid and a whitespace-only flag, so review can hide cosmetic churn and dirty-overlap logic can split safe vs blocked hunks.

Take / revert

Accepting an incoming hunk or reverting a local block flows through the same validated incoming-mutation boundary as full reconciliation.

13

History — undo / redo

A custom history layer over Lexical that records workspace transactions, so a programmatic action (format a book, apply a fix) is one undoable unit spanning multiple chapters — not a flurry of keystroke-level steps.

runTransaction

Active actions wrap their seam commit in history.runTransaction({ label, candidates, run }); the captured before/after lets undo restore the exact pre-action workspace state.

Update classifier

classifyEditorContentUpdate decides per editor update whether it's a first-snapshot, a no-op, a history-merge, a programmatic-ignore, or a real typing step — keeping the undo stack meaningful.

The usfm-onion boundary

All heavy USFM work — parse, lint, format, diff, fixes, the marker catalog — lives behind one async interface backed by a Rust/WASM engine (usfm-onion-web). The app holds tokens, never raw parsing logic.

Method Does
getMarkerCatalog() Per-marker metadata (category, family, paragraphCategory, payload, closingBehavior, block behavior) — the taxonomy source.
parseUsfm / parseUsfmBatch* USFM text → tokens (+ optional lint). Batch-from-paths is desktop-only (Rust parallel).
lintExisting / lintScope Lint already-parsed tokens, one or many chapters.

Cross-cutting invariants & decisions

The load-bearing rules. Break one and the system gets subtly wrong in ways tests may not immediately catch.

1 Dependency direction

src/core never imports app/web/tauri. Domain stays portable; platforms inject at boot.

2 One live truth, commit-only

All workspace state is WorkingFilesStore; you never mutate it in place — you commit(patch, meta) and let the two channels fan out.

3 The seam is mandatory

Active mutations go through withWorkingFilesDraft: draft → compute → validate identity → re-check gate → commit → invalidate. No side effects in mutate; none at all on abort.

4 Saved ≠ versioned ≠ published

Disk write, git checkpoint, and remote publish are independent substates; the later two failing is a warning, not a save failure.

5 Never accept remote while review remains

finalizeOutcome structurally forbids a fast-forward when any review diff is pending; partial acceptance adopts on the next save.

6 Single-source marker taxonomy

Form-mode categories derive from the usfm-onion catalog, not hand-maintained sets; only the rule grouping + uncatalogued legacy markers stay local, and they're labeled.

7 Two recovery surfaces

The coarse gate blocks all mutation; the fine recovered-conflict tracker forces review and blocks incoming sync until resolved.

8 Lossless modes

regular / flat / form all round-trip through the same token stream; mode is a Lexical shape, never a content change.

9 Structure, not repair

Chapter/verse markers carry their bytes in node shape, not hidden editable text — the byte-corruption class is unrepresentable, not swept. Bad states are surfaced as findings, never silently fixed; a dev-only fixpoint assert guards tokens ≡ lex(join(sources)).

10 Line endings preserved

The model is LF-internal; each chapter's disk eol is re-applied at serialize, and chapters never reorder — so CRLF files and stored chapter order round-trip without phantom diffs.

11 One findings store, two producers

onion lint and sous content analysis land in one namespaced FindingsStore through one presentation policy and one decoration path; findings anchor by token id or (sid, UTF-16 span).

Glossary — the nouns

Term Meaning
USFM Unified Standard Format Markers — the backslash-marker text format scripture is authored in (\p, \v, \f…).
Token One parsed USFM unit (text run, marker, verse number) with id/marker/sid/span. The lossless pivot representation.
SID Scripture identifier — a stable verse/segment address like GEN 1:1; semanticSid is its diff-stable form.
marker A USFM tag (e.g. p, q1, s); the taxonomy groups them into paragraph categories.
Working files The live, in-memory editable state of the open project — ScriptureBookState[] in the store.
Baseline / sourceTokens The last-saved state a chapter is "clean" against; advances on every save (rebase), not just at load.
dirty A chapter whose current tokens differ from its baseline. Drives save, backups, status.
Commit (store) A typed write to the store (commit(patch, meta)) — distinct from a git commit.
Checkpoint A git commit created on save — the local version history. "Versioned," distinct from "saved to disk."
Reconciliation Merging incoming remote changes into the workspace (auto-accept disjoint / behind-only, else manual review).
Scratch / draft A structural-sharing copy the seam mutates safely across awaits before validating and committing.
Reference item A read-only resource (translation notes, another translation) loaded alongside the editable project for comparison.
Provenance Generated as a canonical lay-of-the-land for the codebase, cross-checked against the source (status kinds, relationship kinds, editor modes, pipeline filters, and the save/seam/reconciliation flows verified directly). Treat it as a map, not a contract — when code and map disagree, the code wins; update this file at the next touchpoint.
